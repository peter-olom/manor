Preview isolation QA blocked on ffmpeg imageSetupCommand — image preparation hangs past 10-min broker timeout on arm64 for large package trees.

Jul 23, 09:02 PM

Symptoms
start_preview with imageSetupCommand `apt-get update && apt-get install -y ffmpeg` never advances past pulling_image phase. No preparation container visible in broker list. 4+ attempts failed identically. Small packages (bc) complete in seconds. Client-side fetch timeout ~30s compounds the issue — worker process killed mid-call cancels the lease.
Observations
1. DNS + HTTP to deb.debian.org work (2.6 MB/s throughput, 25MB in 9.5s) — not a network issue. 2. DEBIAN_FRONTEND=noninteractive attempt hung identically — not a debconf prompt. 3. bc (small package) imageSetupCommand completed in seconds — mechanism works for small packages. 4. ffmpeg has a large dependency tree; the hang occurs at the broker image-preparation stage, never advancing past pulling_image. 5. No active preparation container visible in broker list during the hang. 6. Leases 5783f5ee failed, 374732c9 and 0960429f stuck >10min. 7. Worker→butler→broker start_preview HTTP chain times out client-side (~30s) for any setup exceeding that window.
Suspected cause
The Manor preview runtime broker has a 10-minute image-preparation timeout that is insufficient for large apt package installations on arm64. The imageSetupCommand preparation may be pulling/building a large layer synchronously without progress feedback, and the broker either silently stalls or lacks a streaming progress mechanism. The client-side ~30s HTTP timeout on the worker→butler→broker chain causes premature lease cancellation when the worker process is killed mid-call.
Proposed change
Increase or make configurable the broker image-preparation timeout for imageSetupCommand operations. Add progress streaming or polling for imageSetupCommand preparation so the broker reports active progress instead of appearing stuck at pulling_image. Decouple the client-side HTTP timeout from the broker preparation lifecycle so that long-running setup commands don't cause lease cancellation when the worker HTTP call times out. Consider a background/async preparation mode with status polling.
Risk
Increasing timeouts could mask genuine failures. Async preparation adds complexity to lease lifecycle management. Low risk if implemented with progress reporting and configurable limits.
Desired outcome
imageSetupCommand with large package trees (e.g. ffmpeg) completes successfully within a reasonable configurable timeout, with progress visibility and no premature lease cancellation from client-side HTTP timeouts.
